Using Claude Effectively

A guide to model selection, planning workflows, and context management.

Model Overview

Three models, three price tiers, clear roles. Pick the cheapest model that is capable enough for the job.

Never use Opus to write code

Opus costs up to 5× more per token than Sonnet. Its purpose is to think through problems and produce plans that cheaper models can execute. Using Opus to implement code is wasteful and offers no meaningful quality gain for routine engineering work. Once a plan exists, switch to Sonnet or Haiku.

How to Approach a Change

Use this chart to pick the right workflow before you write a single prompt.

The opusplan Model in Claude Code

Claude Code ships a built-in model shorthand called opusplan. It automates the plan-then-implement handoff:

  1. The planning phase runs on Opus — high-quality reasoning over the problem.
  2. Once a plan is approved, Claude Code automatically switches to Sonnet for implementation.

The tradeoff is the context window: opusplan caps at 200K tokens. This is enough for most day-to-day tasks, but it becomes a limitation when:

  • You need to load a large codebase into context.
  • Your planning conversation itself accumulates a lot of back-and-forth.
  • You are doing domain-specific work that requires extensive background documentation — see OpenSpec below.

OpenSpec — Domain-Specific Workflows

For work that has a strong domain component — custom business logic, non-obvious architectural constraints, decisions with long-term consequences — a plan alone is not enough. You also need to capture the why so that future implementers (human or AI) understand the reasoning, not just the outcome.

OpenSpec is a workflow that does this. A spec document is committed alongside the code, making the rationale a first-class artifact in the repo.

When to use OpenSpec

  • The feature touches domain rules that are not obvious from the code.
  • There are real trade-offs between approaches that need to be recorded.
  • A future developer reading the code would otherwise have to reverse-engineer intent.
  • You anticipate revisiting this area and want the context to still make sense in six months.

Recommended workflow

  1. Open a fresh conversation using full Opus (not opusplan) — 1M context gives you room to include background docs, existing code, and long planning discussions.
  2. Work with Opus to reason through the problem, weigh options, and produce a plan.
  3. Ask Opus to write the spec document. It should capture the goal, the options considered, the decision made, and the reasons why.
  4. Open a new window with Sonnet and hand it the spec. Sonnet implements the plan without burning expensive Opus tokens on routine code generation.
Why full Opus, not opusplan?

opusplan has a 200K context limit. Domain-specific workflows often require large context: existing code, design documents, domain references, or extended planning dialogue. Running on full Opus gives you the full 1M context window so nothing has to be left out of the planning stage.

Non-Domain Work — grill-me + Plan Mode

For complex changes that don't require preserving domain knowledge, skip the full spec and use Claude Code's plan mode combined with the grill-me skill.

The grill-me skill

The grill-me skill, created by Matt Pocock, produces a much better plan than going straight into plan mode alone. Rather than requiring you to know exactly what you want up front, it analyses the codebase and asks you the important questions — surfacing edge cases, hidden assumptions, and failure modes before any plan is written. Your initial input can be rough; the skill sharpens it through dialogue.

Claude Code plan mode

  1. Invoke grill-me. Claude analyses the code and asks clarifying questions to surface what matters.
  2. Answer the questions. Your responses don't need to be polished — the skill works with uncertainty.
  3. Enter plan mode. Claude uses the grilling session to produce a well-informed plan.
  4. Review and approve the plan, then exit plan mode. Sonnet implements.

Context Management — Stay or Start Fresh?

Every conversation accumulates context. At some point you need to decide: keep going in the same window, or open a new one and hand over a summary?

Stay in the current chat when

  • The conversation contains useful thought history — reasoning that informed earlier decisions and might still be relevant.
  • The context is not yet strained; the model can still hold everything comfortably.
  • The next step is a direct continuation of the current work.

Start a new window when

  • Most of the context has been consumed by planning and exploration that is now resolved.
  • The next step is implementation, and you do not want the model spending tokens re-processing old reasoning.
  • You planned in full Opus (1M context) and want to implement in Sonnet — be mindful that Sonnet also has a 1M context window, but if your planning session grew very large, distilling it into a handover doc first keeps the implementation window clean.
Context window mismatch

If you planned using full Opus (1M context) and switch to a model with a smaller window, you cannot simply carry the whole conversation over. Distil the planning session into a precise handover document first — the decision made, the reasoning behind it, the constraints uncovered, and the exact next steps — then open a new window with that document as the opening prompt. This is not a concern with opusplan, which handles the handoff automatically within its 200K limit.

Capture before you switch

Even when context windows match, a long planning conversation is noisy. Ask the current session to produce a handover doc before switching — the new model gets the distilled insight without having to process the full dialogue.
